When you run evaluations with multiple trials (`trials_per_task > 1`), waza quantifies how far the results can be trusted. This page explains the statistical fields in your results JSON.

---

## When Statistical Fields Appear

- Per-task fields (`tasks[].stats.pass_rate_ci`, `tasks[].stats.bootstrap_ci`) appear when a task ran more than one trial.
- Suite fields (`summary.statistics`) appear when `trials_per_task > 1` and at least two tasks ran.

Single-trial runs skip statistical analysis.

---

## Pass-Rate Confidence Interval (`pass_rate_ci`)

`tasks[].stats.pass_rate_ci` is a 95% [Wilson score interval](https://en.wikipedia.org/wiki/Binomial_proportion_confidence_interval#Wilson_score_interval) on the task's pass rate across its trials. Wilson stays inside [0, 1] and keeps its coverage at the 3–10 trials typical of agent evals, where normal-approximation and bootstrap intervals come out too narrow ([Bowyer et al., 2025](https://arxiv.org/abs/2503.01747)).

```json
"stats": {
  "pass_rate": 0.8,
  "passed_runs": 4,
  "total_runs": 5,
  "pass_rate_ci": { "lower": 0.3755, "upper": 0.9638, "mean": 0.8, "confidence_level": 0.95 }
}
```

Interpretation: 4 of 5 trials passed, but the task's true pass rate could plausibly be anywhere from about 38% to 96%. A wide interval means you need more trials before trusting the pass rate.

`summary.statistics.success_rate_ci` is the same interval for the suite's `success_rate`, counting each task as one sample.

`waza run` prints both:

```text
Success CI95:   [6.1%, 79.2%]
...
      pass_rate=80.0% [CI95 38-96%]  avg=0.85  ...
```

## Reliability (`pass_hat_k`)

`summary.statistics.pass_hat_k` is the pass^k curve from τ-bench ([Yao et al., 2024](https://arxiv.org/abs/2406.12045)). Element *k−1* is the probability that *k* fresh trials of a task **all** pass, averaged over tasks. For a task with *c* passes in *n* trials, the unbiased estimate is C(c, k) / C(n, k). The curve runs up to the fewest trials any task ran.

pass^1 is the average per-trial pass rate. The drop from pass^1 to pass^n shows how much of that rate comes from tasks that pass only some of the time, which is what users of a skill experience as unreliability.

```json
"statistics": {
  "pass_hat_k": [0.7333, 0.5667, 0.4667, 0.4, 0.3333]
}
```

```text
Reliability:    pass^1=73%  pass^2=57%  pass^3=47%  pass^4=40%  pass^5=33%
```

Interpretation: a single trial passes 73% of the time, but five trials of the same task all pass only 33% of the time.

<Aside type="note">
With `max_attempts > 1`, a trial that passes on a retry counts as passed, so these intervals and pass^k describe reliability *with* retries.
</Aside>

## Score Confidence Interval (`bootstrap_ci`)

`tasks[].stats.bootstrap_ci` is a percentile [bootstrap](https://en.wikipedia.org/wiki/Bootstrapping_(statistics)) interval (10,000 resamples) over the task's weighted trial scores, and `summary.statistics.bootstrap_ci` is the same over per-task average scores. The dashboard shows the per-task interval next to each task's weighted score.

```json
"bootstrap_ci": { "lower": 0.72, "upper": 0.95, "mean": 0.85, "confidence_level": 0.95, "num_bootstraps": 10000 }
```

With only a few trials a bootstrap interval is too narrow, so prefer `pass_rate_ci` when judging pass/fail reliability.

---

## Significance (`is_significant`, no longer populated)

Earlier versions set `is_significant` to `true` when a task's `bootstrap_ci` excluded zero. That interval is on the task's own score, which can't be negative, so the check only asked whether the score was above zero. It compared nothing, so neither the flag nor the dashboard's "significant" badge indicated statistical significance. It is no longer populated, and older results files that contain it still load.

Significance applies to a **difference**, such as with-skill minus baseline. The intervals on this page describe each run on its own, so comparing two runs' intervals cannot establish whether a change is real: overlapping intervals can still hide a significant difference, and runs over the same tasks need a paired comparison of per-task results.

## Normalized Gain (`normalized_gain`)

**Normalized Gain** measures improvement as a percentage of the maximum possible gain, useful for comparing progress across different score ranges.

### Formula

```
Normalized Gain = (Actual Score - Baseline Score) / (1.0 - Baseline Score)
```

### Structure

```json
{
  "task": "code-quality",
  "baseline_score": 0.60,
  "improved_score": 0.75,
  "normalized_gain": 0.375
}
```

### Interpretation

| Scenario | Baseline | Improved | Gain | Normalized Gain |
|----------|----------|----------|------|-----------------|
| **Low starting point** | 0.40 | 0.60 | 0.20 | 0.33 (33%) |
| **High starting point** | 0.80 | 0.90 | 0.10 | 0.50 (50%) |

In the second example, a 0.10 improvement from 0.80 is more impressive (50% of remaining room) than a 0.20 improvement from 0.40 (33% of remaining room).

### When to Use

- Comparing tasks with different baseline scores
- Measuring effectiveness of an improvement across multiple tasks
- Aggregating progress across heterogeneous benchmarks

## Using These Fields for CI/CD Gating

```yaml
- name: Run evaluations with 10 trials
  run: waza run eval.yaml --trials 10 -o results.json || true  # the next step decides

- name: Gate on the success-rate interval
  run: |
    python3 << 'EOF'
    import json, sys
    with open('results.json') as f:
        results = json.load(f)

    ci = (results['summary'].get('statistics') or {}).get('success_rate_ci')
    # Fail only when even the optimistic end of the interval misses the target.
    if ci and ci['upper'] < 0.8:
        sys.exit(f"❌ success rate CI95 [{ci['lower']:.0%}, {ci['upper']:.0%}] is below the 80% target")

    # Flag tasks whose pass rate is still too uncertain to trust.
    for task in results['tasks']:
        task_ci = (task.get('stats') or {}).get('pass_rate_ci')
        if task_ci and task_ci['upper'] - task_ci['lower'] > 0.5:
            print(f"⚠️  {task['display_name']}: pass-rate CI95 wider than 50 points; add trials")
    EOF
```

### Gate Strategies

| Strategy | When | Check |
|----------|------|-------|
| **Interval vs target** | Avoid failing on noise | `success_rate_ci.upper` below target fails |
| **Interval width** | Too few trials to judge | `pass_rate_ci` width above your tolerance |
| **Reliability** | Users need consistent behavior | `pass_hat_k[k-1]` below target for your *k* |
| **Normalized gain** | Cross-task comparison | Gain > 0.25 (25% of room) |

## Minimal Trials Recommendations

| Complexity | Min Trials | Typical | Rationale |
|-----------|-----------|---------|-----------|
| Simple, deterministic | 3 | 5 | Low variability |
| Standard LLM tasks | 5 | 10 | Moderate variability |
| Complex multi-step tasks | 10 | 20 | High variability |
| Critical production gates | 20 | 30 | Stringent confidence |

## Example Results JSON

Three tasks with 5 trials each; the tasks passed 5, 4, and 2 of their trials (fields abridged):

```json
{
  "summary": {
    "total_tests": 3,
    "succeeded": 1,
    "failed": 2,
    "success_rate": 0.3333,
    "statistics": {
      "bootstrap_ci": { "lower": 0.52, "upper": 0.93, "mean": 0.74, "confidence_level": 0.95, "num_bootstraps": 10000 },
      "success_rate_ci": { "lower": 0.0615, "upper": 0.7923, "mean": 0.3333, "confidence_level": 0.95 },
      "pass_hat_k": [0.7333, 0.5667, 0.4667, 0.4, 0.3333]
    }
  },
  "tasks": [
    {
      "display_name": "deploy-to-azure",
      "status": "failed",
      "stats": {
        "pass_rate": 0.8,
        "passed_runs": 4,
        "total_runs": 5,
        "flaky": true,
        "pass_rate_ci": { "lower": 0.3755, "upper": 0.9638, "mean": 0.8, "confidence_level": 0.95 },
        "bootstrap_ci": { "lower": 0.71, "upper": 0.97, "mean": 0.86, "confidence_level": 0.95, "num_bootstraps": 10000 }
      }
    }
  ]
}
```

A task's `status` is `passed` only when every non-skipped trial passed. So when every task ran *n* trials and none were skipped, `success_rate` equals pass^n, the last element of `pass_hat_k`.
