**Release candidate, November 23, 2026.** Publication and package verification
are pending; the [download reference](../../reference/releases/) retains the
latest verified published version.

Dogfooding v0.42.0 exposed a familiar gap: a command can finish its model call
and still fail the workflow around it. This patch focuses on that last mile,
along with cases where Waza accepted an option without honoring its contract.
It does not add another evaluation mode or expand the production-integration
claims introduced in [v0.42.0](../v0-42-0/).

The [repository blog post](https://github.com/microsoft/waza/blob/main/docs/blog/v0.42.1-hotfix.md)
summarizes the dogfood lessons and upgrade considerations.

## Upgrade deliberately

Once publication is verified, upgrade a standalone installation with
`waza update`. For the azd extension, check `azd waza --version` independently:
its package publication and registry synchronization are separate from the
standalone release.

Existing generated workflows are files in your repository; upgrading Waza
does not rewrite them. Review their pins and agent-execution settings before
adopting a regenerated template. An offline harness pass is not an assessment
of model quality.
Standalone skill scaffolds share `init`'s pinned, offline-default CI policy.
Mock results and missing or unknown executor identities fail the manual agent
gate rather than being accepted as agent evidence.

The `go-jose` patch adds a default 4096-bit RSA key-size limit and removes
`RandReader`. Embedders using larger keys or that dependency API should review
the upstream migration notes before upgrading.

### Proposed Copilot SDK v2 migration

The SDK migration in [PR #1118](https://github.com/microsoft/waza/pull/1118)
is open and may change before merge. As proposed, Waza keeps launching the
bundled Copilot CLI as a separate process rather than adopting the v2 SDK's
in-process default, and it still refuses to fall back to a CLI found on `PATH`.
A custom Copilot CLI supplied through `COPILOT_CLI_PATH` must speak protocol 4.
In the proposal, protocol-3 runtimes, including CLI 1.0.85, fail at startup
before a session is created. Use the bundled runtime or a protocol-4 CLI.

For prompt graders with `evidence_context`, an override must identify the pinned
embedded executable. Owned native execution rejects any nonempty
`COPILOT_CLI_PATH` override; clear the variable to use the embedded runtime in
either case.

`waza models --json` is not fully unchanged: the formerly optional, deprecated
`billing.tokenPrices.cachePrice`, `billing.tokenPrices.contextMax`,
`billing.tokenPrices.longContext.cachePrice` and
`billing.tokenPrices.longContext.contextMax` fields are absent from the v2 SDK.
Scripts that read them must adapt: the v1 SDK points consumers to
`cacheReadPrice` and `maxPromptTokens`, respectively, when available. Those
fields are optional too.

The [migration PR](https://github.com/microsoft/waza/pull/1118) reports local
guarded Go and compatibility tests, lint and cross-compilation checks on
earlier revisions. At an earlier PR head
`2a2d29c7465ef6c9c7d1d50649abbc248064f23b`, the
[Windows Go CI job](https://github.com/microsoft/waza/actions/runs/45300281018/job/138130813320)
ran guarded tests on a merge of the proposal and its base; the
[Ubuntu evaluation](https://github.com/microsoft/waza/actions/runs/45300280939/job/138130812629)
used a mock engine. Neither establishes an authenticated Windows model
evaluation at that head; a source-bound record for that specific evaluation has
not been verified. Live evidence and full platform validation on the final
integrated source, plus checks of the distributed packages, remain pending.

## What verification establishes

The [release procedure](https://github.com/microsoft/waza/blob/main/docs/RELEASE.md)
requires qualification of the exact reviewed source before tagging. Published
binary and extension checks must use the actual distributed bytes, not a
same-source rebuild. Checksums establish artifact identity, not execution.
Native smoke results, authenticated dogfood results and registry availability
must be reported separately, including any unavailable evidence.
