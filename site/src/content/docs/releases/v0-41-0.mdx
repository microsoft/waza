## A deliberately bounded source inventory

This preview compares the verified published v0.40.1 source
`e0c251df896bee4e0f9b38a693a6105bf7eadd19` with the immutable initial
preparation base `6750ff6115b3a98a5609bd751227bca629839a9c`.
Both the standalone `v0.40.1` and extension
`azd-ext-microsoft-azd-waza_0.40.1` tags resolve to that baseline.
Both historical tags retain **`0.39.1` in `version.txt` and `extension.yaml`**.
The [historical release-source explanation](../../reference/releases/#capabilities-introduced-in-v0390)
documents tag-injected linker version `0.40.1` for the published binaries despite
those older manifests. These immutable tags remain valid source-comparison
anchors, not a new verification of binary provenance or proof that their
manifest mismatch was corrected. The exact-matching target metadata contract
applies prospectively to v0.41.0; it does not rewrite historical tags.

The [source comparison](https://github.com/microsoft/waza/compare/e0c251df896bee4e0f9b38a693a6105bf7eadd19..6750ff6115b3a98a5609bd751227bca629839a9c)

### Answer native questions without inventing user intent

Opt-in `config.native_user_input: true` gives scenario agents the SDK
`ask_user` tool. Task `user_input_responses` supply ordered answers with optional
question matching, then the adaptive responder can answer. Unexpected questions
fail rather than receiving a default answer
([#818](https://github.com/microsoft/waza/pull/818)).
Result writers use schema **1.9**, recording actual
`runs[].user_input_requests`; absent observations are not reconstructed.
This capability is separate from the bounded exact-unit runner profile.
See [native questions](../../guides/eval-yaml/#answer-native-agent-questions).

### Preserve recovery and distinguish operational failure

Merged source preserves completed results and partial recovery snapshots after
trial timeout with bounded cleanup and shared-client replacement
([#870](https://github.com/microsoft/waza/pull/870)).
Force-stop callbacks that finish during cleanup are joined within the existing
grace ([#883](https://github.com/microsoft/waza/pull/883)).
Operational grader failures remain distinct from ordinary false assertions
([#925](https://github.com/microsoft/waza/pull/925)).
Workspace capture is bounded and retains explicit diagnostics rather than
inventing complete file evidence
([#845](https://github.com/microsoft/waza/pull/845), issue
[#830](https://github.com/microsoft/waza/issues/830)).
These source changes do not settle the remaining cleanup-summary, recovery,
or native Windows admissions listed below.

### Prepare local dashboard views once per snapshot

Local run-list and summary projections are cached for each successfully loaded
snapshot, with defensive copies for callers and transactional refresh behavior
([#858](https://github.com/microsoft/waza/pull/858)).
Run summaries and details use native JSON encoding while keeping absent skill
metadata distinct from an explicitly recorded empty skill
([#857](https://github.com/microsoft/waza/pull/857)).
These changes do not invent missing observations, change historical results, or
turn a cached view into new execution evidence. See the
[dashboard guide](../../guides/dashboard/).

### Avoid repeated capture and dependency work

Native capture readers reduce repeated source-buffer conversions and
reconstruction work while retaining bounded validation and owned-buffer
handling ([#833](https://github.com/microsoft/waza/pull/833)).
This is not broader native workflow support or a claim of measured release-wide
performance gains.

Local dashboard builds reuse locked dependencies when the package manifests
are unchanged. `make web-deps-force` is the explicit recovery path for stale or
corrupt installed dependencies
([#837](https://github.com/microsoft/waza/pull/837)).
Dependency reuse does not replace the actual dashboard build or its asset
admission.

Exact-source release validation, rooted asset handoff, and completeness

#### Durable execution, recovery, and aggregation

The v0.41.0 roadmap [#755](https://github.com/microsoft/waza/issues/755) is
closed. The new [durable execution operations guide](../../guides/durable-execution/)
walks the connected path below
([#982](https://github.com/microsoft/waza/pull/982)).

- **Separate logical work from execution attempts**
  ([#764](https://github.com/microsoft/waza/issues/764)) - The attempt core
  ([#942](https://github.com/microsoft/waza/pull/942)) gains public
  `waza runner submit` / `POST /api/v1/submissions` and read-only
  `waza runner lineage` / `GET /api/v1/lineage`
  ([#970](https://github.com/microsoft/waza/pull/970)), plus a Lab lineage view
  ([#973](https://github.com/microsoft/waza/pull/973)). Distinct submissions
  always reserve a new execution ID; reuse makes zero engine calls. Historical
  results gain no synthesized attempts.
- **Compatible resumability and checkpoints**
  ([#765](https://github.com/microsoft/waza/issues/765)) - Captured checkpoints
  and protected Lab recovery ([#959](https://github.com/microsoft/waza/pull/959),
  [#961](https://github.com/microsoft/waza/pull/961)) are joined by read-only
  `waza runner checkpoint availability`, its protected API and a Lab action
  that report whether a checkpoint can resume and why not, without executing
  or reserving work ([#976](https://github.com/microsoft/waza/pull/976)).
- **Execution lifecycle semantics**
  ([#767](https://github.com/microsoft/waza/issues/767)) - A bounded, chained
  lifecycle journal derives each attempt's state, cancellation, deadline,
  partial completion, advisory retry eligibility and allowed actions; stale
  dispatched attempts report `orphaned`. Earlier attempts report
  `observation: "unobserved"` and no records are rewritten
  ([#979](https://github.com/microsoft/waza/pull/979)).
- **Complete execution evidence states**
  ([#768](https://github.com/microsoft/waza/issues/768)) - Protected evidence
  capture libraries ([#958](https://github.com/microsoft/waza/pull/958)) and
  aggregate members that show verified retry/branch parents and declared
  evidence lineage, with a Lab legend for all five evidence states
  ([#972](https://github.com/microsoft/waza/pull/972)). Originals and retries
  stay separate; no winner is chosen. See the
  [evidence review guide](../../guides/evidence-review/).
- **Aggregate completed manifests independently**
  ([#766](https://github.com/microsoft/waza/issues/766)) - The execution-aware
  standalone aggregation core ([#960](https://github.com/microsoft/waza/pull/960))
  and an end-to-end CLI/API state matrix proving byte-identical, order-independent
  reports with usage withheld when incomplete
  ([#969](https://github.com/microsoft/waza/pull/969)).
- **Optimizer adapter contract**
  ([#790](https://github.com/microsoft/waza/issues/790)) - `waza optimize
  capabilities` and `waza optimize run` evaluate adapter-proposed candidates
  with the existing runner and graders against a pinned suite with held-out
  qualification. Spend is `measured` or `unavailable`; no hard cap is claimed
  ([#975](https://github.com/microsoft/waza/pull/975)). See
  [optimizer adapters](../../guides/optimizer-adapters/).

## Preserve the published hotfix baseline

The [v0.40.1 article](../v0-40-1/) already covers selected-task coverage, strict
token-budget exits, grouping, hooks, saved-run identities, artifact paths,
first-event startup, and JavaScript grader input. They are not new v0.41.0
changes. The JavaScript grader fix has a patch-equivalent main commit
([#882](https://github.com/microsoft/waza/pull/882)).
The other seven hotfix commits are outside the initial main ancestry. Direct
tree comparison identifies differences in strict token exit handling, hook
templating, and relative adversarial artifact paths, among other baseline
surfaces. The three demonstrated contract regressions were subsequently
restored in merged #953 with production-caller regressions and native
Linux/Windows validation. **This draft does not claim that main preserves all
v0.40.1 fixes.** The final candidate must retain those regressions.
Former Unreleased changelog entries are folded into the v0.41.0 entry; their
presence alone is not proof of inclusion since the published baseline.
Unmerged work, predicted performance, native-platform results, and runtime
frontier work are not release evidence.
