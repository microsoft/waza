## Run one explicit unit

From a source checkout with embedded dashboard assets built:

```bash
go build -o waza ./cmd/waza
./waza runner capabilities
./waza runner run < examples/runner/request.json > selected.runner.json
./waza runner validate-result < selected.runner.json
```

The request captures one eval and task source. It explicitly selects shard,
task ID, trial and attempt. The runner never expands globs, scans adjacent tasks,
automatically retries or converts a missing observation into success. Request
and result size limits are 4 MiB and 16 MiB. JSON admission rejects duplicate
keys, unknown fields, wrong/null types, invalid Unicode, trailing documents and
out-of-range integers; captured YAML rejects unknown/duplicate fields,
aliases/anchors and unsupported floats.
The example selects `shard-a / selected / trial 2 / attempt 2` despite the eval
declaring three trials/attempts and an adjacent-task glob.

`selection.shard` must equal the captured input shard; `selection.task` must
equal the authored task ID. `trial` and `attempt` are one-based and bounded by
the declared eval; omitted/zero `max_attempts` is one. Disabled tasks, a
conflicting tuple, unsupported source semantics and ambiguous/missing selectors
fail before execution. Use exact source files and explicit task IDs; never
resolve ambiguity by choosing a neighboring task. See the
[migration guide](../runner-migration/) for before/after command examples and
the complete adapter matrix.

The current profiles support single-turn mock/native execution with inline
resources, text checks and ambient skills disabled. Unsupported source semantics
fail explicitly. Native execution additionally requires
`allow_paid_execution: true` and required capability `inline.native-text`; it can
incur usage. The example uses mock execution and does not authorize paid calls.

## API, schemas and negotiation

`waza serve` (alias `waza dashboard`) exposes `POST /api/v1/runner/run` with the same request/result as
the CLI. Send `Content-Type: application/json`; cross-origin calls are rejected.
Execution accepts only `localhost` or literal loopback Host names, not DNS aliases;
this is a local service, not a remotely authenticated execution endpoint.
`GET /api/v1/runner/capabilities` advertises supported versions and capabilities.
HTTP 200 carries application failures too: inspect the terminal outcome.

- Request bootstrap schema, selected runner and terminal result are independently
  versioned `1.0`; identity derivation is `sha256-json-v1`.
- Offering `["2.0","1.0"]` permits the supported `1.0` fallback;
  offering only `["2.0"]` fails before execution.
- Unknown required capabilities fail closed; unknown optional ones are recorded
  as unavailable. Neither implies a silent feature substitution.
- [Request schema](https://github.com/microsoft/waza/blob/main/schemas/runner-request-1.0.schema.json)
  and [result schema](https://github.com/microsoft/waza/blob/main/schemas/runner-result-1.0.schema.json)
  are validated offline.

The [canonical developer/user contract](https://github.com/microsoft/waza/blob/main/docs/RUNNER_CONTRACT.md)
defines fields, normalization, digest namespaces, evolution and failure boundaries.
Its [frozen identity vector](https://github.com/microsoft/waza/blob/main/internal/runnercontract/testdata/identity.json)
is tested across subprocesses and the normal Linux/Windows Go CI.
Comments, YAML mapping order and LF/CRLF do not change logical identity; material
source/selection changes do. Identical logical IDs do not imply deduplication or
exactly-once execution.

The identity test vector is version `sha256-json-v1` and canonical digest
`1c43e5f40d3d15fc7fa686e5892812aa60c0a507007a15648c5abf7817787819`.
The fixture file contains the exact run/shard/task/trial/attempt IDs. The digest
binds declared canonical input, not runtime/environment attestation.

## Terminal outcomes

| Outcome | Exit code | Interpretation |
|---|---:|---|
| `success` | 0 | Graded selected attempt passed |
| `evaluation_failure` | 1 | Check failure |
| `infrastructure_failure` | 2 | Setup/execution/shutdown/output failure |
| `canceled` | 3 | Observed cancellation |
| `timeout` | 4 | Deadline exceeded |
| `unsupported_capability` | 5 | Runner version/capability mismatch |
| `invalid_request` | 6 | Schema/source/selection/profile rejection |

Every recoverable runner path converges on one validated envelope. SIGKILL,
machine loss or an unwritable channel cannot promise output; missing output is
unknown, never success. Missing identity/usage/observation remains unavailable.
Exactly-once is limited to one terminalization/write attempt within a live
process; it is not exactly-once execution or deduplication. Abrupt host loss or
broken output can leave no envelope. The full contract documents the result
schema, outcome examples, diagnostic codes and failure boundaries. Deterministic
tests cover every state without paid/live execution.

## Migration and container walkthrough

Use `runner adapt` only with two explicit supported source files:

```bash
./waza runner adapt --eval path/to/eval.yaml --task path/to/task.yaml \
  --run-key qualification-42 --shard shard-a --task-id selected \
  --trial 1 --attempt 1 > request.json
```

The adapter preserves source bytes. It never silently removes unsupported skills,
hooks, CSVs or multi-turn behavior; retain `waza run` for those workflows.
Historical result IDs and schemas are not rewritten.

For the bounded Linux-container proof of concept:

```bash
git lfs pull
bash examples/runner/build.sh
bash examples/runner/smoke.sh --local
bash examples/runner/test.sh
```

This builds a static binary with Go `1.26.4`, uses OCI `scratch`, and records a
local image ID. The smoke checks
`.runner-reference/output/unit.runner.json` against the exact task, attempt and
identity vector. Supported host assumptions, expected output, diagnostics and
maintainer update procedure are in the
[bounded reference guide](../runner-reference/). No public image digest is
available; do not treat a tag, local ID or placeholder as a published pin.
There is no scheduler-specific code or strong-isolation claim.

## Dashboard status

`GET /api/v1/lab/runner-results` exposes validated `*.runner.json` artifacts,
including negotiation, exact selection, identity lineage and terminal state.
Open **Runner results** at `/#/lab/runner` with `waza dashboard --lab` (or
`waza serve --lab`). The read-only view displays the recorded negotiation,
requested/resolved tuple, pre-execution validation, no-adjacent-work indication,
identity hierarchy/digest/version, terminal outcome/exit code/failure boundary,
envelope validation and linked diagnostics. It does not derive success from HTTP
200 or observation status. Use **Refresh runner results** to reload explicitly;
API errors, unsupported/malformed data and empty archives remain distinct.
The synthetic demo does not request or invent runner results.
See [the Lab guide](../dashboard-lab/#inspect-terminal-runner-results) for details.
Compatibility adapters (#761) and the bounded reference (#762) require **no
dashboard UI change**.
