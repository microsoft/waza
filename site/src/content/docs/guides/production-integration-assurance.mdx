> **Package 1.0 · v0.42.0 · candidate.** Evidence-linked qualification guidance for the v0.42.0 production-integration contracts. This package describes the checked-in candidate; the qualification workflow separately binds its exact run and outputs. Neither is a blanket readiness certificate or deployment-specific risk assessment.

This is an operator qualification aid, not a blanket production-readiness guarantee or a substitute for deployment-specific risk assessment. Evidence for the #769–#774 contracts is linked below; this package adds **no new Lab dashboard view**.

Source evidence links are pinned to the `v0.42.0` release tag. The source package remains a candidate until tag-release qualification completes; its offline builder verifies each evidence file against the checked-out source.

| --- | --- | --- | --- | --- |
| Runner request, artifact store, terminal, and provenance bundle | An attacker or storage fault alters inputs, artifacts, outcomes, or adds unbound bundle members after execution. | Provenance verification recomputes canonical identities and outcome bindings, checks digests and signatures, and rejects unbound or irregular bundle members. Inventory and terminal readers validate their closed profiles. | Verification is only as trustworthy as the verifier binary, the operator-supplied key, and the storage from which the original expected digest was obtained. | [Offline provenance verification](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_PROVENANCE.md)<br />[Provenance verifier tests](https://github.com/microsoft/waza/blob/v0.42.0/internal/provenance/provenance_test.go)<br />[Inventory verification](https://github.com/microsoft/waza/blob/v0.42.0/docs/COMPONENT_INVENTORY.md) |

Keyless CLI verification requires an independently supplied Sigstore root and exact issuer plus workflow identity policy. Both check signed claims against bundle members. | Local-key custody and root distribution remain operator responsibilities. ## Production-readiness checklist

- [ ] **Record the exact Waza version, runner API profile, worker OS, runner image digest, and operator trust anchors for each deployment.** — The evidence names immutable digests and the installed CLI's observed version; do not treat a tag, request, or configured identity as proof of execution. `pin-and-identify`. Evidence: [Runner capabilities and identity contracts](https://github.com/microsoft/waza/blob/v0.42.0/docs/RUNNER_CONTRACT.md)<br />[Provenance verification and pinning](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_PROVENANCE.md)
- [ ] **Verify the component inventory and its attestation against the exact image digest before admitting a reference image.** — Keep the verifier report and attestation result for the digest actually consumed. For images without an inventory, republish explicitly or record that the evidence is unavailable. `verify-image-inventory`. Evidence: [Inventory generation, verification, and image attestation](https://github.com/microsoft/waza/blob/v0.42.0/docs/COMPONENT_INVENTORY.md)<br />[Qualified tag-release reference-image publication workflow](https://github.com/microsoft/waza/blob/v0.42.0/.github/workflows/publish-runner-reference.yml)<br />[Operator example](https://github.com/microsoft/waza/blob/v0.42.0/examples/runner/assurance/README.md)
- [ ] **If adopting optional execution provenance, select local Ed25519 or GitHub Actions OIDC signing and distribute verifier trust out of band.** — For opted-in provenance, require a verified report bound to the exact request, pinned image/version, artifact manifest, objects and outcome. Keyless additionally requires workflow identity/issuer policy and approved root. Signing is not a release requirement; managed KMS remains unavailable. `verify-provenance`. Evidence: [Provenance CLI and verification procedure](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_PROVENANCE.md)<br />[Provenance contract schemas](https://github.com/microsoft/waza/blob/v0.42.0/schemas/provenance-statement-1.0.schema.json)
- [ ] **Inspect the budget matrix on every worker OS and set unsupported policy to reject when an unenforceable limit would make the work unsafe.** — Accept only limits shown enforced by that host. Treat CPU/RSS as runner-process measurements where available, not per-attempt quotas; do not claim disk or process-count accounting. `check-host-budgets`. Evidence: [Per-OS budget capability matrix](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_BUDGETS.md)<br />[Budget example request](https://github.com/microsoft/waza/blob/v0.42.0/examples/runner/budget-unit.json)
- [ ] **Enforce the execution boundary outside Waza and run isolation preflight inside the final worker/container boundary before dispatch.** — Require evidenced off-host network/remote-tool restrictions under the no-non-loopback-interface condition. Do not infer filesystem, environment, or subprocess isolation from host declarations or inconclusive probes. `prove-external-isolation`. Evidence: [Isolation preflight and provider limits](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_ISOLATION.md)<br />[Isolation contract schema](https://github.com/microsoft/waza/blob/v0.42.0/schemas/execution-isolation-1.0.schema.json)
- [ ] **Derive telemetry only from completed contract evidence and choose an approved OTLP/HTTP receiver and payload policy.** — Confirm the receiver, access controls, retention, and identifier handling; use the default payload exclusion unless digest disclosure is explicitly accepted. `export-telemetry-deliberately`. Evidence: [Post-run telemetry inputs and export behavior](https://github.com/microsoft/waza/blob/v0.42.0/docs/EXECUTION_TELEMETRY.md)<br />[Telemetry 1.0 schema](https://github.com/microsoft/waza/blob/v0.42.0/schemas/execution-telemetry-1.0.schema.json)
- [ ] **Keep queueing, placement, leases, retry policy, and delivery guarantees in the external scheduler; dispatch through one adapter call per descriptor.** — Exercise the external scheduler's failure, duplicate-delivery, and retry behavior independently. Treat adapter provenance `not_configured` as no verification. `integrate-adapter`. Evidence: [Adapter contract and limitations](https://github.com/microsoft/waza/blob/v0.42.0/docs/RUNNER_ADAPTERS.md)<br />[Portable adapter example](https://github.com/microsoft/waza/blob/v0.42.0/examples/runner/adapter/submit.json)
- [ ] **Use the existing Lab panels to inspect published evidence and diagnostics; do not assume the assurance package adds a new dashboard view.** — Correlate each view with its source contract and preserve the JSON/report used for the operator decision. `inspect-existing-lab-evidence`. Evidence: [Existing Lab evidence and navigation](https://github.com/microsoft/waza/blob/v0.42.0/site/src/content/docs/guides/dashboard-lab.mdx)<br />[Versioned assurance package](https://github.com/microsoft/waza/blob/v0.42.0/docs/PRODUCTION_INTEGRATION_ASSURANCE-1.0.json)
- [ ] **After every Waza or runner-image upgrade, re-negotiate capabilities, re-verify the consumed image inventory, and reassess the deployment against this package version.** — Compare the new schemas and package applicability to the previous evidence; regenerate signed evidence for the upgraded image and retain any unavailable or unsupported states. `reassess-after-upgrade`. ## Verification limits

- This package describes the v0.42.0 source candidate and the listed public contract profiles; it does not certify every Waza binary, image, host, runtime, scheduler, model, or deployment.
- Waza local Ed25519 and opt-in GitHub Actions OIDC signatures are offline-verifiable only relative to independently supplied trust; keyless additionally requires workflow identity and issuer policy. Fake-service conformance is not live public-good signing evidence. Managed KMS remains unavailable. Signing is not a release requirement; GitHub artifact attestations separately cover qualification outputs.
- Candidate image and inventory evidence remains in workflow-run artifacts. Registry publication and inventory attestation occur only in the qualified tag-release path; previously published digests are not retroactively covered.
- Telemetry is derived from completed runner documents and can be exported as files or OTLP/HTTP JSON; there is no live execution-path telemetry emission.
- Budgets enforce wall time, model-turn, and tool-call limits only. CPU and memory observations are process-scoped on supported OSes and are not per-attempt limits; disk and process-count accounting are unavailable.
- Isolation evidence proves only off-host network and remote-tool boundaries when no up non-loopback interface is present. Loopback remains reachable; Waza does not enforce filesystem, environment, subprocess, or general sandbox boundaries.
- Adapters translate one descriptor to one public runner call. No scheduler is included; the optional provenance hook runs only when an operator configures a verifier.
- A green local test or documentation-site build establishes repository conformance only; it is not a deployment-specific assessment, penetration test, vulnerability scan, or production workload measurement.

## Migration and reassessment

- **Migration:** The package and its evidence links are additive; they do not change runner request, terminal, manifest, or adapter wire contracts.
- **Older runners:** Older runners do not implement these v0.42.0 features and may reject newly added contract fields. Negotiate the installed runner's capabilities and upgrade deliberately before depending on an optional profile.
- **Previously published images:** Images published before inventory attestation remain uncovered; the tag-release publisher refuses to replace an existing versioned image tag, and existing image digests are not retroactively covered.
- **After upgrades:** For each Waza or image upgrade, verify the exact consumed digest, refresh inventory and provenance evidence, repeat host capability/preflight checks, and review updated limitations rather than inheriting a prior qualification.
