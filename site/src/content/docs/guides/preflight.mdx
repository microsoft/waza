---
title: Offline Eval Preflight
description: Inspect local prerequisites and descriptive requirement references without starting an agent or service.
---

`waza preflight` builds an agent-free inventory of an eval's local prerequisites.
It does **not** replace `waza check` skill readiness or execute the evaluation.

**Available in v0.39.0:** install the published standalone release or run
`waza update` before these commands. See [availability](../../reference/releases/) and the
[credential-free Quick Start](../../quick-start/).

```bash
waza preflight eval.yaml
waza preflight eval.yaml --context-dir ./fixtures --format json > preflight.json
waza preflight eval.yaml --strict
waza preflight examples/preflight/eval.yaml --format json
```

## Meaning and exit policy

| State | Meaning | Default exit policy |
|-------|---------|---------------------|
| `verified` | A static declaration, reference, or local dependency check passed | 0 |
| `unresolved` | Evidence is unavailable or cannot be checked offline | Warning; 0, or 1 with `--strict` |
| `unsupported` | The selected reader/executor cannot provide a requested capability | Warning; 0, or 1 with `--strict` |
| `invalid` | Configuration, references, paths, or integrity checks are invalid | 1 |

Usage/output errors retain the CLI's configuration-error exit 2. This new command
does not change `run`, `grade`, `check`, or `gate` exit policies.

**Verified never means requirement satisfied, runtime enforcement established,
or external state changed.** A plausible answer or success message does not prove
that a remote object was created, a command had the intended effect, or a
forbidden side effect did not occur. Inspect actual captured state with suitable
existing graders. A mock response tests the harness, not live agent quality.

Preflight never initializes or calls an engine/model, executes graders or hooks,
starts subprocesses, launches MCP/CLI mocks or live services, probes credentials,
fetches module/schema references, or runs update checks. It makes only local
reads. Live services, model access, interpreter syntax, credential/permission
availability, Git revision materialization, and conditional checkpoint execution
remain unresolved.

Exit policy is driven by `diagnostics`, not every entry in the capability
inventory. For example, the `mock` executor lists MCP support as `unsupported`,
but that alone does not fail `--strict` when the eval does not request MCP.
A well-formed configured MCP dependency on that executor adds a `runtime.mcp`
diagnostic; that unsupported-capability diagnostic warns by default and fails
with `--strict`. Malformed MCP configuration also produces an `invalid`
diagnostic and fails by default, regardless of strict mode.

Required-skill discovery follows runtime discovery: malformed skill or agent
definitions are warned about and skipped without printing their parsing
payloads. An unrelated malformed definition does not invalidate a valid required
skill. A required name that cannot be discovered still fails validation.

Inspection is synchronous. `Inspect` has no context/cancellation parameter, and
the command does not use a canceled Cobra context to skip local inspection.
There is no cooperative cancellation or deadline guarantee for local filesystem
reads; this limitation does not permit model or service calls.

## Descriptive requirements

Task YAML can attach stable IDs to observable outcomes, forbidden effects,
recovery expectations, and qualitative checks. IDs are local to the task.

```yaml
id: save-record
name: Save a local record
inputs:
  prompt: Create record.json with the requested local data.
graders:
  - name: persisted
    type: file
    config:
      must_exist: [record.json]
  - name: no-unrelated-file
    type: file
    config:
      must_not_exist: [unrelated.json]
requirements:
  - id: record-present
    category: outcome
    description: The record exists in captured workspace state.
    checks:
      - scope: task
        grader: persisted
  - id: no-unrelated-effects
    category: boundary
    description: The unrelated local artifact was not created.
    checks:
      - scope: task
        grader: no-unrelated-file
```

Each requirement needs a nonempty description and a unique, nonempty ID without
leading or trailing whitespace. Categories are `outcome`, `boundary`, `recovery`,
and `quality`.
`checks` select existing **explicit** grader declarations:

| Scope | Selection |
|-------|-----------|
| `eval` | One `eval.yaml` grader with the selected `name` |
| `task` | One task-level grader with the selected `name` |
| `checkpoint` | One grader at the selected `after_turn` (required, 1-based) |

`after_turn` is forbidden outside checkpoint scope. Several requirements may
share a grader. Empty/absent `checks` means **uncovered/unresolved**, not success.
Unknown references, duplicate requirement IDs, repeated identical checks, or
ambiguous declarations within a scope are invalid configuration.

Distinct eval/task scopes can have the same grader name; references still
resolve, but current flattened final results may overwrite same-name results.
Preflight reports this as `grader.result_collision` **unresolved attribution**,
not an invalid declaration. Use distinct names before joining runtime evidence.
Implicit agent-policy and synthesized expectation graders are not referenceable.

Metadata never adds assertions or changes runtime grading. Equivalent valid
tool paths remain permitted unless the referenced existing grader explicitly
requires a sequence. A post-run boundary grader detects recorded violations; it
does not prevent side effects. A checkpoint may not run if execution stops before
its turn. These limitations apply even when references resolve.

## Local resolution

Static grader validation leaves caller-owned tool-argument declarations
unchanged and disables external JSON Schema loading. Program declarations are
checked for their required command without loading project timeout defaults or
launching a process; runtime constructors still resolve their existing defaults.

Task globs and `tasks_from` CSV paths resolve from the eval directory. Nonempty
`tasks_from` retains runtime precedence over YAML task lists; CSV range, ID
fallback, variables and template rules are shared with execution. CSV rows do
not acquire invented requirements.
An individual valid task glob may match nothing if another pattern supplies
tasks; malformed globs and an entirely empty discovered inventory are invalid.
Any present `scenario` must be a nonblank string with exact
`schemaVersion: "2.0"`, including in raw native YAML/JSON parsing. Null and
non-string values no longer fall back to legacy admission or scalar coercion.
Remove `scenario` for a legacy suite, or supply the valid identity/version pair;
truly absent fields retain legacy defaults.
CSV paths must be lexically within the eval directory and remain within it after symlinks resolve, including
when the eval directory itself is a symlink or filesystem/volume root. Fallback IDs/names use the original
1-based data row, so selecting `range: [2, 2]` retains `row-2`, not `row-1`.
Regrading and run analysis use the same CSV loader: results from that range can
be regraded with `waza grade eval.yaml --results results.json --task row-2`, or
by omitting `--task` to grade all selected tasks. Explicit CSV IDs/names and
template variables retain their precedence. Contained links remain allowed;
resolved escapes are rejected. The final CSV read uses a retained eval-directory
root so late symlink replacement cannot escape it; concurrent file contents are
not frozen.
An aliased eval base allows relative contained sources and absolute paths within
the lexical alias root. An alternate physical absolute spelling outside that
lexical root is rejected even when it resolves inside; physical equivalence alone
does not grant admission.
Contained absolute CSV paths retain their actual source in task plans and
diagnostics; relative sources still resolve from the eval directory.

Default fixtures are `<eval-directory>/fixtures`. CLI `--context-dir` resolves
from the process cwd, as does the existing task `context_dir` override.
Resource/instruction paths must stay workspace/context relative. Native volume
prefixes are rejected using the host platform's path rules; a colon alone is not
an absolute-path marker on POSIX (for example, `reports/run:1.json`). Rooted paths
starting with `/` or `\` remain invalid on every host. Local resource
and instruction files are inspected, never modified. File-backed resource paths
containing `..` within any cleaned segment are diagnosed as rejected by the
existing runtime loader; rename the file or segment. Inline content retains its
existing path handling except that workspace-root destinations (`.` or any path
cleaned to `.`) are invalid for resource/instruction and file/diff checks,
including inline resource destinations. `inputs.context.fixture`
accepts files or directories from the eval directory with runtime symlink
containment rules. Explicit skill directories resolve from the eval directory;
`required_skills` follows existing eval-level declaration discovery. Relative Git
source paths resolve from process cwd, as at runtime. Source existence is local
evidence, not verification of a commit or successful worktree creation.

Legacy suites and scenarios with an explicit target also receive the same
read-only `.waza.yaml` workspace skill-directory defaults as `waza run` when eval
directories are omitted. Explicit eval directories take precedence. Disabled
scenario discovery does not inspect or inject ambient project skills.

Scenario-bearing evals require exact explicit `schemaVersion: "2.0"` with a
nonempty `scenario`. Existing v1 suites retain their version/default/discovery
semantics. The approved scenario loader determines requested skill discovery:
an absent, null, empty, or whitespace-only target with no explicit directories
means no ambient discovery. Nonblank target names and explicit directory values
retain their original spelling. Explicit null/empty targets still fail the
embedded eval schema; their parsed discovery intent is not ambient discovery.
Task
`skill_directories: []` disables it. The actual SDK discovery control is native
`EnableSkills=false`, not an empty-directory proxy; preflight records static
intent without constructing a session. `.agent.md` tools use native
SKILL.md/agent/cwd/directory discovery precedence and report requested
allowlist/deny-all as unresolved, never proof of enforcement or observed behavior.

Command-mock fixtures resolve from the eval directory. Task `command_mocks`
replaces eval mocks, including explicit `[]`. Task `mcp_mocks` replace only the
same-named eval MCP mocks and are listed as dependencies of their task. A task
mock that fails to decode, such as an invalid matcher, is reported as
`task.configuration` with its task file; fixture and admission failures are
reported as `mock.mcp` with the task file and task id. When a task cannot be
decoded offline, for example because a matcher references an external schema,
its MCP mocks are still checked for executor, schema version, names and fixtures.
Same-name MCP mocks replace live server declarations; a live server that every
task replaces with its own mock is not inspected. An eval MCP mock that every
task replaces is reported as `mock.mcp_replaced` and is not listed as a
dependency; its fixtures are not read, but its inline tool declarations are
still validated. `waza run` admits eval mock fixtures the same way, against the
tasks selected to run. MCP fixture responses and matchers are parsed
without starting a mock. External schema references are not fetched.
Fixture and inline `input_schema` must be a JSON object when supplied; strings, numbers,
booleans and arrays are invalid. Omitting it retains the default tool schema.
Input schemas are checked independently of response matchers: an unavailable
response schema does not hide an invalid input schema. Offline fixture loading
retains resolved declarations for this inventory even when response validation
fails; that partial configuration is not executable or verified.
Live stdio/HTTP/SSE settings also use the runtime's full side-effect-free decoder;
malformed headers, environment maps or arguments are invalid, not just unresolved
live availability.

Native argument matchers compile eagerly while reading YAML. Preflight guards
the same source bytes before that decoder, including `tool_calls.expect` and
`tool_constraint` argument matchers in eval/task/checkpoint declarations,
pinned cached presets, and merged overrides. External schema prerequisites
stop that materialization with an unresolved diagnostic and `complete: false`;
ordinary matcher literals and MCP returned payloads are not treated as schemas.
Invalid static grader fields still fail by default when the same pinned preset
or merged override also has an unavailable schema. Inline and fixture-backed MCP
responses retain both invalid regex configuration and unresolved schema
prerequisites, across responses and declaration order. Finite mock source errors
also do not suppress independent eval, task, or checkpoint grader diagnostics.
Task sequence eligibility is checked against the enclosing eval version before
offline decoding; an unavailable grader schema cannot hide an unsupported sequence.
These mixed cases report
`invalid` plus an `unresolved` diagnostic and keep `complete: false`; a regex or
static-field failure never makes an external schema prerequisite verified.
Later grader schema-file and MCP input-schema compilation also sets
`complete: false` when external evidence cannot be inspected.
Existing runtime loaders retain their normal resource-loading behavior.
Only the explicit offline external-reference denial is unresolved; unrelated
schema loader failures remain invalid and fail the default preflight policy.

Every remote grader requires a valid matching `waza.lock`, just as execution
does. Missing/malformed locks, missing entries, or digest mismatch are invalid.
A missing pinned cache is unresolved; populate it explicitly with `waza get`
while online. Cache integrity is not trust or grading success. Locked grader
dependencies use the effective expanded name: an explicit alias overrides the
preset name, with the export filename supplying the fallback for unnamed presets.
An unnamed unresolved reference remains unnamed until its preset is available.
Requirement references to eval graders use that known effective identity even
when the preset and override cannot be merged. If a valid unnamed remote
reference has no known identity yet, a zero-match requirement lookup is
**unresolved**, not invalid or verified: the unavailable preset could supply the
name. Known nonmatching names, duplicate matches, malformed references and
invalid requirement metadata remain invalid. Authored failed-merge declarations
are not rewritten to achieve this reporting lookup.
Local grader
`schema_file`, rubric, trigger and snapshot paths retain their runtime resolution
bases; relative schema/rubric paths resolve from cwd, while snapshots use the
grader's `context_dir` when configured.
With `update_snapshots: true`, a missing snapshot leaf that resolves within its
runtime context is **unresolved**, not invalid: preflight neither creates it nor
verifies write permissions. Missing snapshots without update mode, invalid
containment, unreadable files, dangling symlinks and non-file paths remain invalid.

## JSON report and compatibility

The report has `kind: "waza.preflight"` and its own `schemaVersion: "1.0"`.
Its independent contract is `schemas/preflight.schema.json`; invalid authored
requirement metadata remains visible in failed reports instead of preventing
diagnostic serialization.
It contains `source`, `executor`, `complete`, `tasks`, `capabilities`,
`dependencies`, and `diagnostics`. `complete` means inventory examination
completed, **not satisfaction, enforcement, live readiness, or valid config**.
Partial reports retain actionable diagnostics and do not silently verify
unexamined evidence.

Diagnostics contain stable `code`, `state`, `severity`, `source`,
optional `task_id`/`requirement_id`, `message`, and `remediation`.
Configuration/credential payloads are not included in messages; authored
requirement descriptions are intent, not secrets storage.

Use a CLI build containing #660 for this command. Requirements remain optional
descriptive metadata in existing v1 tasks; older readers can ignore them.
No new hard runtime semantics or global artifact-version bump is introduced.
A minimum-version note or ignored minor field is not enforcement. Future hard
semantics must choose a separate explicit artifact boundary older readers reject.
Preflight reports are not evaluation results and do not create dashboard runs.
Only the exact string `kind: "waza.preflight"` is reserved for this result-reader
fence; unknown same-major result fields, including non-string `kind` values,
retain normal compatibility behavior.
