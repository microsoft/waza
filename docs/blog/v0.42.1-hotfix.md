# Waza v0.42.1: close the dogfood loop

**Release candidate, November 23, 2026.** This post describes the selected
hotfix work, not a completed publication.

Dogfooding is useful precisely because it follows the whole workflow. In
v0.42.0, task generation could finish inference on Windows and then fail when
it tried to read a session file. A skill scaffold could accept an explicit
output directory and still write into an ancestor workspace. Successful model
calls and zero exit codes were not enough.

The v0.42.1 patch targets those gaps without introducing another evaluation
mode. Its selected scope also removes the nonexistent `azd waza generate`
example, rejects unsupported token output formats, connects scaffolded trigger
examples to development reports, and makes generated CI release-pinned with
explicit agent execution.

The reviewed dependency patch
[microsoft/waza#1103](https://github.com/microsoft/waza/pull/1103) also updates
`go-jose/v4` to 4.1.6 for GHSA-mgcc-cww5-fp2q. Its default 4096-bit RSA limit
and removed `RandReader` API need attention for affected embedding applications.

The planned scope also includes a Copilot SDK migration, tracked by
[microsoft/waza#1117](https://github.com/microsoft/waza/issues/1117) and
proposed in the open pull request
[microsoft/waza#1118](https://github.com/microsoft/waza/pull/1118). It is not
merged, and the details below may change before release.

The published v0.42.0 uses `github.com/github/copilot-sdk/go` v1.0.34 with
bundled Copilot CLI 1.0.112. The proposal moves to
`github.com/microsoft/copilot-sdk/go/v2` v2.0.1 with bundled CLI 1.0.114, which
speaks SDK protocol 4. It keeps Waza's existing spawned-process runtime instead
of adopting the SDK's in-process default, and it intends to keep session
policy, provider, permission, results and transcript contracts unchanged.

The SDK and its bundled runtime move together. A custom Copilot CLI supplied
through `COPILOT_CLI_PATH` must speak protocol 4. In the proposal, protocol-3
runtimes, including CLI 1.0.85, fail at startup before a session is created.
Use the bundled runtime or a protocol-4 CLI.

For prompt graders with `evidence_context`, an override must identify the pinned
embedded executable. Owned native execution rejects any nonempty
`COPILOT_CLI_PATH` override; clear the variable to use the embedded runtime in
either case.

`waza models --json` is not fully unchanged. The formerly optional, deprecated
`billing.tokenPrices.cachePrice`, `billing.tokenPrices.contextMax`,
`billing.tokenPrices.longContext.cachePrice` and
`billing.tokenPrices.longContext.contextMax` fields are absent from the v2 SDK.
Scripts that read them must adapt: the v1 SDK points consumers to
`cacheReadPrice` and `maxPromptTokens`, respectively, when available. Those
fields are optional too.

The [migration PR](https://github.com/microsoft/waza/pull/1118) reports local
guarded Go and compatibility tests, lint and cross-compilation checks on
earlier revisions. At an earlier PR head
`2a2d29c7465ef6c9c7d1d50649abbc248064f23b`, the
[Windows Go CI job](https://github.com/microsoft/waza/actions/runs/45300281018/job/138130813320)
ran guarded tests on a merge of the proposal and its base; the
[Ubuntu evaluation](https://github.com/microsoft/waza/actions/runs/45300280939/job/138130812629)
used a mock engine. Neither establishes an authenticated Windows model
evaluation at that head; a source-bound record for that specific evaluation has
not been verified. Live evidence and full platform validation on the final
integrated source, plus checks of the distributed packages, remain pending.

The [download reference](../../site/src/content/docs/reference/releases.mdx)

## What changes for users

After publication, standalone users can upgrade with `waza update`.
Extension users should check `azd waza --version` separately: the extension
package and its registry entry have independent publication steps.

Upgrading does not rewrite an existing generated workflow. Review its release
pins, path filters and execution settings before adopting the new template.
Offline validation establishes harness/configuration behavior, not model
quality or permission to run an agent.
Standalone skill scaffolds use the same pinned, offline-default CI policy as
`init`. A mock result cannot pass the manual agent-execution gate.

## Keep the evidence attached

The hotfix must pass qualification on its exact merged source before tagging.
Package smoke must use the distributed binaries and extension archives.
A same-source rebuild is useful evidence about source, but it is not evidence
that the bytes users downloaded ran successfully. The release record will
separate package checks, native execution, registry availability and any
authenticated dogfood limitations.
